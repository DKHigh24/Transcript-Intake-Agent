Transcript Intake Agent

Electronics AI Working Group  ·  Operating Manual  ·  Last updated June 2026

Overview

This system ingests DOCX meeting transcripts from the Electronics AI Working Group, extracts AI opportunities, classifies them against the AI Acceleration SharePoint framework, and produces weekly and monthly HTML reports for human review.

What goes inWhat comes out
DOCX transcript file dropped in input/transcripts/Weekly HTML report (5-tab layout: Cards, Analytics, Full Table, Trends, Progress)
Session date (auto-detected from filename)Monthly HTML summary for the same calendar month
GitHub Copilot subscription (default) or OpenAI API key (optional override)Excel workbook for human review (review_rows.xlsx)
SharePoint payload JSON (draft, human-gated)
ADO PAT + org config in .env (optional)Azure DevOps Issues for each approved opportunity — tracked through execution
💡
All outputs are draft-only. Nothing is pushed to SharePoint automatically. Human review is always required before any SharePoint submission.

3 — Back-Dated Transcripts Auto-Rebuild Triggered

If you add a transcript whose date is earlier than the most recently processed transcript, the pipeline detects this automatically and rebuilds all weekly and monthly reports so that every report reflects the complete longitudinal data set.

✅
You do not need to do anything differently. Just run the same --mode weekly command. The rebuild happens automatically.
# Example: adding a transcript from 5/14 when you already have 5/27, 6/3, 6/10
.\.venv\Scripts\python.exe src\main.py \
  --input "input/transcripts/Electronics AI - Working Session - 5_14_2026.docx" \
  --mode weekly

# Output will include:
#   Back-dated transcript detected (2026-05-14 <= existing max 2026-06-10)
#   Rebuilding ALL weekly and monthly reports ...

Force a date override

If the filename does not contain the correct date, pass it explicitly:

.\.venv\Scripts\python.exe src\main.py \
  --input "input/transcripts/my_transcript.docx" \
  --mode weekly \
  --date 2026-05-14

5 — Manual Classification (Last Resort — No Copilot, No OpenAI) Manual Step Required

If neither Copilot access nor an OpenAI key is available, you can provide output/classified_rows.json manually. This is a fallback only — the Copilot SDK path (§4) should work for anyone with a GitHub Copilot subscription.

1

Run dry-run to chunk the transcript

.\.venv\Scripts\python.exe src\main.py \
  --input "input/transcripts/YOUR_FILE.docx" \
  --mode dry-run

This writes output/transcript_chunks.json — read these chunks to understand the session content.

2

Write classified_rows.json manually

Create output/classified_rows.json as a JSON array using the 40-field schema. Reference an existing archived week's file as a template:

output/weeks/2026-06-10/classified_rows.json

Required fields include: Title, OperatingBucket, LevelOfAnalysis, AIUseCaseType, SignalStrength, PrimaryFunctionChoice, CurrentStatus ("(2) Needs Review"), and all other fields from the schema.

⚠️
Choice values must match config/choice_values.json exactly, including intentional typos:
 • "Crosss-Functional/Governance" (3 s's)
 • "Leve 6 - Action/Automation" (missing l)
3

Run the weekly pipeline

The pipeline detects the existing classified_rows.json and skips AI steps automatically.

.\.venv\Scripts\python.exe src\main.py \
  --input "input/transcripts/YOUR_FILE.docx" \
  --mode weekly

9 — Azure DevOps Push (opt-in) After Human Review

After reviewing the weekly output, you can push approved opportunities to Azure DevOps as tracked Issues. This is always opt-in and always follows human review.

💡
Why ADO? Without a work tracking system, the group cannot answer "we talked about invoice matching automation three weeks ago — has anything happened?" ADO integration closes that loop by creating a tracked Issue for each opportunity and syncing its live status back into every report automatically.
1

Review the output first

Open output/weeks/<date>/review_rows.xlsx. Verify titles, problem statements, evidence summaries, owners, and next steps. Only push rows you are confident are accurate.

2

Run the pipeline with --push-ado

.\.venv\Scripts\python.exe src\main.py \
  --input "input/transcripts/YOUR_FILE.docx" \
  --mode weekly --push-ado

Each row without an ADOWorkItemId is created as an ADO Issue under the parent Epic configured in .env.

3

Check the Progress tab

Open the weekly report and click the Progress tab. All newly pushed items appear under "Queued (To Do)" with ADO chip badges linking directly to their ADO work items.

✅
Safe to re-run. If you run --push-ado again, the pipeline checks ADO by title before creating. If an item with that exact title already exists, it recovers the existing ID instead of creating a duplicate.

12 — Keeper Rules

  • Never commit .env files or API keys to the repository.
  • Never push directly to SharePoint — all payloads are draft-only and require human review.
  • Always use .\.venv\Scripts\python.exe — not the system Python.
  • Run --mark-processed after every manual pipeline run to keep the watcher manifest current.
  • When editing classified rows manually, run --mode rebuild afterward so all HTML reports reflect the change.
  • The output/ folder is gitignored — do not commit generated reports or artifacts.
  • Choice field values must match config/choice_values.json exactly — including the known typos.
  • The default AI backend is GitHub Copilot SDK. If no OPENAI_API_KEY is set, Copilot is used automatically. Do not set a dummy key — leave it unset to stay on Copilot.
  • ADO push (--push-ado) is always opt-in and always follows human review. Never run it before reviewing the output workbook.
  • Step 0 ADO sync is read-only — it never creates or modifies ADO work items. Only --push-ado creates items.
  • ADO PAT is a secret — never commit it to the repository. Keep it only in .env.

Appendix A — Plain English Guide

This section explains the entire system without technical language. If you're new to this tool or just need a refresher, start here.

What is this thing, really?

Every week your Electronics AI Working Group meets and talks about ways the business could use AI. Those conversations get recorded and turned into a Word document (a transcript). Without this tool, someone would have to read through hours of conversation, pull out the interesting ideas, fill out a bunch of spreadsheet fields for each one, and organize them into a report.

This tool does all of that automatically. You drop in the Word document, it reads through the conversation, figures out which parts are talking about AI opportunities, writes up a structured description of each one, and creates a polished report you can share with leadership.

💡
The short version: Meeting transcript goes in → organized AI opportunity report comes out. A human still reviews everything before anything goes anywhere official.
🔗
And then what? The tool can also push each approved opportunity into Azure DevOps as a tracked work item, then automatically check each week whether anyone has picked it up. The weekly report's Progress tab answers "we talked about X three sessions ago — where does that stand?" without anyone having to manually look it up.

What does the AI actually do?

There are two moments where AI is used. Everything else is just regular computer logic:

1

Reading for ideas

The AI reads each section of the transcript and asks itself: "Is someone describing a way AI could help here?" It pulls out the moments that look like real opportunities and ignores the small talk, agenda items, and one-off comments.

2

Filling out the form

For each opportunity it found, the AI fills out a detailed description — things like: who brought it up, how risky it is, how ready the organization is for it, what the next step should be, and whether a human needs to approve it before anything happens. Think of it like the AI filling out a long intake form for you.

Everything the AI produces is marked as a draft. Nothing gets sent anywhere — no SharePoint, no email, nothing — until a real person reviews it and approves it.

What AI brain does it use?

The tool is smart enough to use whatever AI access you already have:

If you have this…It uses this…
A company OpenAI API keyOpenAI (ChatGPT's engine)
A GitHub Copilot subscription (like the one running this assistant)GitHub Copilot — no extra key needed
NeitherYou fill out the form yourself using an existing week as a template

For most people at Acuity, the answer is the middle row — your Copilot subscription covers it.

Step by step: what happens when you run it

1

You drop the Word document into a folder

The transcript file goes into the input/transcripts/ folder on your computer. That's it. The file just needs to have the date in its name (e.g., 6_17_2026).

2

You run one command

You open PowerShell (the blue command line window) and type a single command. That's the whole job on your end. Everything else is automatic.

3

The system reads and cleans the transcript

It opens the Word document, strips out formatting noise, and splits the conversation into chunks — one chunk per speaker turn or topic. Like breaking a book into paragraphs before reading it.

4

It filters for the relevant parts

Not every sentence in a meeting is about AI. The tool scans for keywords — things like "agent," "automate," "Copilot," "model," "workflow" — and sets aside the parts of the conversation that don't seem relevant. This step uses no AI at all; it's just simple text matching, like a search function.

5

AI reads the relevant chunks and picks out the opportunities

Now the AI reads only the filtered sections (never the full transcript) and identifies the actual ideas worth capturing. It looks for things like: a demo someone shared, a repeated manual process someone mentioned, a tool someone is already using, or a governance question the group raised.

6

AI fills out the details for each opportunity

For each idea it found, the AI completes a structured record — about 40 fields covering things like who owns it, how complex it is, whether it needs a human in the loop, and what the recommended next step is. All of this gets saved as a draft.

7

It builds your reports

The tool creates three things: an Excel spreadsheet (for review), a SharePoint data file (draft, not sent yet), and a polished HTML report you can open in any browser. The report has five views: a card layout, charts, a full table, a trends view that shows how ideas are evolving week over week, and a Progress view that shows the live status of every opportunity that has been submitted to Azure DevOps.

8

It files everything away

The week's data is saved into a history folder. Every previous week's report gets updated too, so the trend charts always show the full picture — even if you add a transcript from a past meeting later.

What if I add a transcript from a past meeting?

No problem. The system checks the date on the file. If the meeting happened before the most recent transcript already processed, it automatically goes back and updates all the reports — every week and every month — so the trend data stays accurate. You don't have to do anything extra.

What does "human review required" mean in practice?

After the tool runs, you get an Excel file and an HTML report. Every row in those files is flagged as "Needs Review." A person on the team looks through them, corrects anything the AI got wrong, and only then decides whether to submit anything to SharePoint. The tool never pushes anything automatically — it just does the prep work.

What could go wrong, and how do I fix it?

The one thing you should never do

🚫
Never submit anything to SharePoint directly from the files this tool produces without a human reviewing them first. The tool is designed to help humans make better decisions faster — not to replace the decision.

OpenSpec Change Workflow

All changes to src/, skills/, and config/ require an OpenSpec change artifact to be created and reviewed before implementation begins. This ensures every code change is backed by documented intent, design rationale, and verifiable specs.

When to Create a Change

  • Any new feature or pipeline stage modification
  • Changes to LLM prompts or extraction logic
  • Updates to classification schema or config JSON
  • New output formats (reports, PPTX, integrations)
  • Bug fixes that affect documented behavior
💡
If you're unsure whether a change needs an OpenSpec artifact, create one anyway. The process is lightweight and keeps the codebase documented.

The Four CLI Commands

CommandWhen to Use
openspec new change "<name>" Start a new change — creates proposal, design, specs, and tasks scaffolding under openspec/changes/<name>/
openspec instructions apply --change "<name>" Get the implementation task list and context files for a change before coding
openspec status --change "<name>" Check artifact completion and change readiness at any point
/opsx:apply <name> (Copilot CLI) Invoke the openspec-apply-change skill to implement all pending tasks for a change

Canonical Specs Location

The folder openspec/specs/ is the authoritative reference for how the current system behaves. It contains one spec per pipeline capability:

SpecCovers
openspec/specs/transcript-ingestion/spec.mdDOCX reading, cleaning, turn splitting, keyword filtering, chunking
openspec/specs/opportunity-extraction/spec.mdLLM candidate extraction from filtered chunks
openspec/specs/opportunity-classification/spec.mdMVP schema classification and validation
openspec/specs/trend-reporting/spec.mdWeekly + monthly HTML trend reports, history store
openspec/specs/meeting-presentation/spec.mdPPTX deck generation for upcoming sessions
📁
When a change modifies a capability, its spec in openspec/specs/ must be updated as part of that change's tasks before archiving.

Typical Workflow

1
Propose — Run /opsx:propose or openspec new change to create the change artifacts.
2
Review artifacts — Check proposal.md, design.md, capability specs, and tasks.md under openspec/changes/<name>/.
3
Implement — Run /opsx:apply <name> to execute all tasks. The agent implements code, marks tasks complete, and verifies the pipeline still runs.
4
Archive — Run /opsx:archive <name> to move the completed change to openspec/archive/ and sync specs to openspec/specs/.
